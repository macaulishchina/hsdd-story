# 批量导出：完整方向图示例

[export.story.xml](export.story.xml) 是设计用模拟数据。代码、检查、操作、人的输入均为虚构案例；所有证据地址使用 `simulation:` 前缀。它说明数据应该怎样表达，不代表本仓库已经实现导出功能或运行了相关测试。

## 打开后应当读到什么

项目要让用户导出当前筛选范围内、最多一万条记录。需求和设计已明确，三条开发分支已经完成；第一次自动回归发现了中文编码问题。后端已做模拟修复，旧联调与测试需要复核，因此需求尚未交付。

当前最直接的下一步是：**重新联调 IG01，再执行 AT01 回归**。人可以先补充验收关注点，之后在人工检查和交付验收节点记录实际体验与结论。

## 从哪里进入

| 层次 | 内容 |
| --- | --- |
| 项目 P01 | 记录管理工具：显示整体目标、当前阻碍和待回应事项 |
| 需求 R01 | 批量导出：需求分析、前提、设计、人工检查、验收与交付 |
| 子需求 R02 | CSV 实现与回归：后端、前端、测试准备、联调和自动回归 |

R02 使用 `parent="R01"` 表示归属。进入 R02 时，需要的父层前提以外部引用节点显示，避免复制一份正式内容。

## 链路怎样组织

需求分析和调研明确现有能力；只读依赖 DP01 与容量假设 AS01 支撑决策 DC01。设计 DS01 经 RV01 评审后，后端 IM01、前端 IM02、测试准备 VT01 可以并行推进，随后共同进入 IG01 联调。

```text
需求分析 → 调研 → 依赖 / 假设 → 决策 → 设计 → 评审
                                               ├─ 后端实现 ─┐
                                               ├─ 前端实现 ─┼→ 联调 → 回归
                                               └─ 测试准备 ─┘

子需求 R02 完成 → 人工检查 → 交付验收 → 发布交付
                                         发布交付 ┄→ 后续异步导出
```

准确的连线以 XML 为准。`requires` 表示完成前提，`references` 提供上下文，`follow_up` 表示后续演进。并行关系由前提关系形成，没有另存“可并行”开关。

## 需要区分的几种状态

| 节点 | 应呈现的情况 | 不能得出的结论 |
| --- | --- | --- |
| AN01 需求分析 | 分析完成 | 整个需求已经完成 |
| IM01 后端实现 | 修订 2 的代码已写，修复尚待复测 | 修复效果已经验证 |
| VT01 测试准备 | 用例与数据就绪 | 导出功能测试通过 |
| IG01 联调 | 旧版曾成功，当前待复核 | 旧成功结果适用于后端修订 2 |
| AT01 回归 | 旧版失败；修复后未复测 | 执行结束等于测试通过，或修复代码完成等于失败消失 |
| AC01 交付验收 | 有关注点，没有接受结论 | 人留下评论等于验收通过 |
| FU01 后续事项 | 本期不做 | 本期交付必须等待异步导出 |

IM01 当前修订为 2，而 IG01、AT01 的 `basis` 仍记录其修订 1。这是有意保留的旧依据，不是引用断链；对应节点的 `validity="needs_review"` 明确提示需要重新核对。

R02 的完成条件是 AT01。R01 的完成条件是 DL01。指定节点及其必要前提均满足，才可以认为相应需求完成；不计算节点完成百分比。

## 人的记录如何保留

- H01 是来自模拟聊天的明确决定，由 AI 记录并已整合到 DC01。
- H02 是页面提交的验收关注点，仍处于 `pending`；AI 尚不能将它视为已经处理或验收接受。
- H03 最初属于 F00。F00 退出当前图后保存在 `archive`，新的 FU01 继续引用 H03；人的原文和最初来源不因整理图而消失。

在网页中，人可以看到这些记录和当前处理情况，并提交新的意见与结论。

## 示例覆盖范围

- 2 个需求容器，含 1 个子需求。
- 16 个当前节点，覆盖全部 13 种节点类型；另有 1 个归档节点。
- 22 条连线：19 条 `requires`、2 条 `references`、1 条 `follow_up`。
- 12 条模拟依据、3 条模拟人的输入、4 条变化记录。
- 包含并行推进、跨层前提、过期依据、失败结果、人工输入、明确完成节点与未来事项。
